## 2．目的

`docs/experiments/initial_experiment_roadmap.md`のEXP-0007として，
変数数$n$の拡大と次数$d_i$の拡大の効果を分離して確認する。EXP-0005で得た
知見（同一設定でも学習seedによって結果が反転しうる）を踏まえ，各ケースを
**3つの独立した学習seedで複製**し，改善が単一runのノイズでないかを検証する。

## 3．仮説

- 両ケースとも，$N_{\mathrm{path}}$が4→8・9へ増えても追跡失敗は起きない。
- 学習済みベジェパスが線形パスを上回る効果は，$n$の増加（ケースA）と
  $d_i$の増加（ケースB）で異なる大きさ・安定性を示す可能性がある。

## 4．多項式系

### ケースA：n3-d222（$n=3$，$(d_1,d_2,d_3)=(2,2,2)$）

- パス数：$N_{\mathrm{path}}=8$
- 候補指数集合：各方程式について$\{(1,0,0),(0,1,0),(0,0,1),(0,0,0)\}$
  （$d_i=2$では次数条件$|\alpha|<2$を満たす指数はこれで全て＝密なサポート）
- 開始系：$g_1=x_1^2-1,\ g_2=x_2^2-1,\ g_3=x_3^2-1$
- 目的系：
  $$f_1=x_1^2+a_{1,1}x_1+a_{1,2}x_2+a_{1,3}x_3+a_{1,4}$$
  $$f_2=x_2^2+a_{2,1}x_1+a_{2,2}x_2+a_{2,3}x_3+a_{2,4}$$
  $$f_3=x_3^2+a_{3,1}x_1+a_{3,2}x_2+a_{3,3}x_3+a_{3,4}$$
- 係数分布：複素一様分布，`bound=1.0`（EXP-0005の`bound`拡大とは独立に，
  $n$・$d_i$拡大の効果だけを見るため意図的に低いboundを維持）
- 観測次元：24，行動次元：8（潜在次元4，ベジェ次数3で不変）
- 評価：`evaluation.seed=32000`，`random_action_seed=42000`（3seed共通）

### ケースB：n2-d33（$n=2$，$(d_1,d_2)=(3,3)$）

- パス数：$N_{\mathrm{path}}=9$
- 候補指数集合：各方程式について$\{(1,0),(0,1),(0,0)\}$
  （$d_i=3$では次数条件$|\alpha|<3$的にはより豊かな support も許容されるが，
  EXP-0004/0005と同じ疎なsupportを意図的に維持し，「次数だけ」を変えた）
- 開始系：$g_1=x_1^3-1,\ g_2=x_2^3-1$
- 目的系：
  $$f_1=x_1^3+a_{1,1}x_1+a_{1,2}x_2+a_{1,3}$$
  $$f_2=x_2^3+a_{2,1}x_1+a_{2,2}x_2+a_{2,3}$$
- 係数分布：複素一様分布，`bound=1.0`
- 観測次元：12，行動次元：8（EXP-0005と同じ次元。$n,$supportが同じで$d_i$のみ増加のため）
- 評価：`evaluation.seed=33000`，`random_action_seed=43000`（3seed共通）

## 6．事前チェック（本実行前）

`bound=1.0`で両ケースとも目的系100件をサンプリングし，線形パス（ゼロ行動）の
追跡成功率を確認した：両ケースとも成功率100%（n3-d222: cost mean=39.07，
n2-d33: cost mean=38.81）。破綻的な失敗がないことを確認して本実行に進んだ。

## 7．実行上のトラブルと対応（OpenBLASスレッド過剰発行）

6run（2ケース×3seed）を28コアマシンでプロセス並列実行したところ，
1コアあたりの実効スループットが単独run時（EXP-0005拡大版，約692 steps/秒）の
約1/12〜1/13（約55〜61 steps/秒）まで低下した。原因はJuliaのOpenBLASが
デフォルトで14スレッドを使用し，6プロセス×14スレッド=84スレッドが28コアを
奪い合っていたためと判明した（本系のヤコビ行列は2×2/3×3の極小サイズで
BLAS多スレッド化は無意味）。ユーザー承認のもとで実行中の6プロセスを停止し，
`OPENBLAS_NUM_THREADS=1`，`JULIA_NUM_THREADS=1`，`OMP_NUM_THREADS=1`を
設定して再実行したところ，スループットが約5.6〜5.9倍改善した
（n2-d33：約360 steps/秒，n3-d222：約306 steps/秒）。本記録の結果は，
この修正後の再実行（run-id末尾`-20260927T145848Z`）のものである。
打ち切った旧run（`-20260927T143716Z`）の不完全な出力は削除済み。

## 9．観察

- **ケースB（n2-d33，次数拡大）は3seed全てで安定して改善**した。改善率の
  母標準偏差（1.03pt）は平均改善（-10.17%）に対して小さく，効果は
  seedに対して頑健と言える。
- **ケースA（n3-d222，変数数拡大）は改善が弱く不安定**だった。seed0のみ
  明確な改善（-4.37%，改善率63%）を示したが，seed1・seed2はほぼ0%
  （改善率49〜55%，ランダムと区別できない水準）。母標準偏差（1.61pt）は
  平均改善（-2.09%）そのものより大きく，**この設定での「改善」は
  seedに依存する不安定な効果であり，再現性のある結論とは言えない**。
- 追跡失敗は両ケース・全seedで0件であり，$N_{\mathrm{path}}=8,9$への拡大自体は
  数値的に問題なく処理できている。

## 10．考察

同じ`total_timesteps=500,000`でも，$n$を増やす方が$d_i$を増やすより
学習を難しくしている可能性が示唆される。考えられる要因：

- **観測次元の増加**：ケースAは観測次元が12→24（ケースBは12のまま）へ
  増えており，同じ学習量でもポリシーが学習すべき入出力関係が複雑になった
  可能性がある。
- **開始解の対称性の破れ方**：ケースAは3変数の対称なPham系で，
  開始解の配置がケースBと異なる構造を持つ。
- **学習が未収束**：`actor_logstd_mean`がどのrunでも減少し続けており，
  ケースAはより多くの学習量を必要とする可能性がある。

`docs/experiments/EXP-0005-linear-vs-bezier/README.md`で提案した
「複数seedでの再現性を先に確認する」という基準に従うと，**ケースB
（次数拡大）は次の段階（$n=3,(4,4,4)$等，Julia並列化を要する規模）へ
進む根拠として十分な安定性を示したが，ケースA（変数数拡大）はこの
基準を満たしていない**。

## 11．実行中の問題

- OpenBLASスレッド過剰発行によるプロセス並列時の大幅な速度低下
  （7．に記載）。`OPENBLAS_NUM_THREADS=1`等の設定で解消した。
  今後プロセス並列でJuliaを複数同時実行する際は，この設定を標準手順とする
  べきである。

## 12．結論

- $N_{\mathrm{path}}=8,9$への拡大は，追跡の正しさの面では問題なく処理できる。
- **次数拡大（n2-d33）は3seedで安定して線形パスを上回り**，改善率平均
  約10.2%・改善率0.76という頑健な結果を得た。
- **変数数拡大（n3-d222）は改善が弱くseed依存**で，1つのseedでしか
  明確な改善が見られなかった。この設定単独では「学習が線形パスに勝てる」
  と結論するには不十分である。
- 変数数拡大と次数拡大は，学習の難しさに対して異なる影響を持つ可能性が
  示された。

## 13．次の実験

- **ケースA（n3-d222）**：`total_timesteps`をさらに拡大するか，
  ネットワーク構造・学習率を見直した上で再検証し，改善がseedに対して
  安定するか確認する。安定しない場合，変数数拡大に特有の学習上の課題
  （観測次元の増加，対称性など）を切り分ける追加実験を検討する。
- **ケースB（n2-d33）**：3seedで安定した改善が確認できたため，
  次の規模（$n=2,(4,4)$等）へ段階的に進める根拠がある。
- 今後プロセス並列でJuliaジョブを複数同時実行する際は，
  `OPENBLAS_NUM_THREADS=1`（および`JULIA_NUM_THREADS=1`，`OMP_NUM_THREADS=1`）
  を標準の実行手順に含める。
- $n=3,(4,4,4)$（$N_{\mathrm{path}}=64$）や$n=4,(3,3,3,3)$（$N_{\mathrm{path}}=81$）
  へ進む前に，Julia側のスレッド並列化（`julia_homotopy.md`が既に想定している
  次の一手）の実装を検討する。
